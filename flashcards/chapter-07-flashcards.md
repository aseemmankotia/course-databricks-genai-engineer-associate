## Chapter 7: Foundation Model APIs and Production Serving — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | Pay-per-token pricing: when to use vs provisioned throughput? | Pay-per-token: unpredictable/variable traffic, dev/test, no minimum cost, billed per input/output token. Provisioned: production, SLA-critical, sustained high traffic, reserved capacity, fixed cost. Exam tip: if scenario mentions 'traffic varies 10×' or 'prototype' → pay-per-token. If 'strict SLA' or '1000 req/sec sustained' → provisioned. |
| 2 | Databricks Foundation Model APIs: which models are available as endpoints? | DBRX (Databricks' MoE model), Llama 2 (7B, 13B, 70B), Llama 3 (8B, 70B), MPT-7B, MPT-30B. All served as managed endpoints via Model Serving. Exam tip: DBRX is Databricks' flagship model. MPT-7B is smallest/fastest. Llama 2/3 70B is largest/most accurate. |
| 3 | Provisioned throughput billing unit and what it guarantees? | Billed per hour for reserved tokens/sec capacity. Guarantees: (1) fixed capacity available 24/7, (2) no rate limiting, (3) predictable cost, (4) consistent latency. Exam tip: provisioned = you pay even if idle. Use when traffic is sustained and predictable, not periodic. |
| 4 | Real-time vs batch inference: latency and use case differences? | Real-time: synchronous API calls, <1 sec latency, user-facing apps (chatbots, fraud detection). Batch: asynchronous Spark jobs on Delta tables, minutes to hours, analytics/ETL. Exam tip: if 'daily dashboard' or 'process 10M records' → batch. If 'customer waits for response' → real-time. |
| 5 | How to secure external model API keys (Azure OpenAI, AWS Bedrock) in Databricks? | Store keys in Databricks Secrets scope. Configure external model endpoint in Model Serving to reference the secret scope. Endpoint injects credentials at runtime. Exam tip: NEVER hardcode keys in notebooks or env vars. Always use Secrets + Model Serving integration. |
| 6 | Smaller models (MPT-7B) vs larger models (Llama 2 70B): cost and latency trade-offs? | Smaller models: faster inference (lower latency), cheaper per token, less accurate. Larger models: slower inference, more expensive, more accurate. Exam tip: if accuracy is equal, ALWAYS choose smaller model for better cost/latency. If strict latency SLA → smaller model. |
| 7 | Pay-per-token pricing: what are you billed for? | Billed per 1,000 input tokens + per 1,000 output tokens. Different rates for input/output (output typically 3-5× more expensive). No minimum commitment. Exam tip: calculate total tokens = (docs × avg_input_tokens) + (docs × avg_output_tokens), then multiply by rates. |
| 8 | Batch inference on Delta tables: which Databricks feature to use? | Use Spark UDF calling Foundation Model API endpoint, applied to Delta table in parallel. Process millions of rows efficiently. Exam tip: batch inference = Spark UDF + Delta table. Real-time = synchronous API calls from application code. |
| 9 | What happens when pay-per-token endpoint hits rate limit? | API returns 'rate limit exceeded' error (HTTP 429). Requests fail or queue. Solution: (1) retry with exponential backoff (temporary), or (2) switch to provisioned throughput (permanent fix). Exam tip: if 'production SLA' + 'rate limits' → provisioned is the answer. |
| 10 | External model endpoints: which providers are supported via Databricks Model Serving? | Azure OpenAI, AWS Bedrock, and custom HTTPS endpoints. Databricks proxies requests and injects credentials from Secrets. Exam tip: use Model Serving external endpoints for governance, monitoring, and secure credential management. Don't call external APIs directly from notebooks. |
| 11 | When is provisioned throughput cheaper than pay-per-token? | When sustained traffic is high and predictable. Break-even depends on token volume and rates. Example: if processing >$120/day worth of tokens and traffic is 24/7, provisioned at $5/hour = $120/day may be cheaper. Exam tip: 'sustained high volume' or 'consistent traffic' → provisioned likely cheaper. |
| 12 | DBRX model architecture: parameters and MoE structure? | DBRX is a Mixture-of-Experts (MoE) model with 132B total parameters, but only activates a subset per token (efficient inference). Databricks' flagship model. Exam tip: DBRX = Databricks model. MoE = faster than dense models of same total param count. |
