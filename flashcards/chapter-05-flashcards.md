## Chapter 5: Agents, Tools, and Function Calling — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | ReAct agent decision loop - list the 3 core steps in order | 1. Observe (get input/tool result), 2. Think (reason about next action), 3. Act (call tool or respond). Then repeat from Observe. Exam tip: ReAct = Reason + Act, distinguishing feature is visible reasoning before each action. |
| 2 | Tool schema for function calling - which 3 fields are required in LangChain Tool definition? | 1. name (string identifier), 2. description (when to use this tool), 3. func (Python callable) or args_schema (JSON Schema for inputs). Exam tip: description is crucial for agent's tool selection accuracy. |
| 3 | DBRX Instruct function calling - does it support function calling via Databricks Foundation Model APIs? | Yes. DBRX Instruct supports function calling through Databricks Foundation Model APIs with OpenAI-compatible format. Exam tip: DBRX, GPT-4, Llama 3.1 all support function calling; distinguish by availability (DBRX native to Databricks). |
| 4 | mlflow.langchain.log_model for agents - what components are serialized? | Agent chain + all Tool objects + tool Python function code (via cloudpickle). Exam tip: Tools are included automatically; no separate registration needed for standard Python functions. |
| 5 | LangChain Tool error handling best practice - should retry logic be in tool function or agent? | Agent decides retry strategy. Tool should catch errors, return descriptive error message as string to agent. Agent reasons about error and chooses next action. Exam tip: Keeps agent in control of decision-making. |
| 6 | Plan-and-Execute agent vs ReAct agent - when to use Plan-and-Execute? | Use Plan-and-Execute when: task needs upfront complete plan, steps are known in advance, no adaptation needed between steps. Use ReAct when: dynamic decision-making needed, agent must adapt based on intermediate results. Exam tip: Plan-and-Execute = plan once, execute all; ReAct = plan-execute-replan loop. |
| 7 | Tool description quality - why does '2-3 word description' cause wrong tool selection? | Function calling models use description for semantic matching to task. Brief descriptions lack context to differentiate similar tools. Best practice: 1-2 sentences explaining when to use tool + example scenario. Exam tip: Description quality directly impacts agent accuracy. |
| 8 | Databricks SQL as agent tool - which API to use: spark.sql() or SQL Warehouse REST API? | Use spark.sql() wrapped as LangChain Tool. Reasons: native Databricks access, no extra auth, direct Delta table access. Exam tip: Prefer Databricks-native APIs (spark.sql) over external APIs (REST) when running on Databricks. |
| 9 | JSON Schema 'type': 'number' in tool schema - what Python type does agent receive? | String (e.g. '50' not 50). LLM returns JSON-formatted strings; tool wrapper must parse to correct Python types. Exam tip: JSON Schema describes format, not Python runtime types. Always parse in tool function. |
| 10 | Agent max_iterations parameter - what happens when limit is reached? | Agent stops execution and returns current state (may be incomplete answer). Used to prevent infinite loops. Exam tip: Set based on expected task complexity; too low = incomplete results, too high = wasted compute on bad loops. |
| 11 | LangChain Tool input schema - format for defining required parameters? | JSON Schema format: {'type': 'object', 'properties': {'param': {'type': 'string', 'description': '...'}}, 'required': ['param']}. Exam tip: Use args_schema field in Tool definition with Pydantic model or dict. |
| 12 | Agent observe step - what does agent 'observe' in ReAct loop? | Initial user input OR tool execution result (success data or error message). Observation triggers next think step. Exam tip: Observe is input to agent's reasoning; think → act produces new observation. |
